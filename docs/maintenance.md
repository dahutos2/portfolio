# ポートフォリオの日次改善

## 責任と正本

日次のCodexスケジュールはこの文書を読み、毎回新しいスレッドで未自動化の更新候補を提示する。
実行時刻・有効状態・日次モデルと推論設定はCodexのスケジュール、ビルド・公開条件は `.github/workflows/deploy-pages.yml` が正本。
提案と承認の履歴は各提案のスレッド、着手後の差分・CI・完了状態は対応するGitHub PRを参照する。標準のautomation memoryは索引として使い、別の台帳、常駐サービス、独自スケジューラを作らない。

日次点検と通常の小さな修正はTerraで行う。難しいセキュリティ判断、認証・秘密情報・移行、複雑な設計変更はAstraによる検討が必要と提案に明記し、根拠・対象範囲・未確定事項を引き継ぐ。対象提案への承認と、そのスレッドのモデルがAstraへ切り替わったことを確認して着手する。指示文だけでモデルが自動的に切り替わるとは扱わない。

日次のデータ収集・公開はGitHub Actionsで継続する。Codexは通常のデータ更新を重複して実装しない。
掲載文の正本は `portfolio.config.yml`、規約は `content/legal/`、動的情報は外部API。
`public/data/`、`public/legal/`、`dist/` は生成物であり編集・commitしない。

## 日次点検

1. ローカルのstaged・unstaged・untracked、リモートmain、未完了PR、前回の提案・承認を確認する。ローカルの未反映作業を公開済みと扱わず、変更を上書きしない。
2. 最新のPortfolio実行と公開先 `build.json` のcommit・run_id・generated_atを照合する。収集成功、CI成功、公開成功、実画面確認を区別する。定期実行の遅延やAPI取得不能を「問題なし」としない。
3. npm・Pythonの現在のlockfileを監査し、Node・pnpm・Python・GitHub Actionsを含め、公式リリース・勧告・サポート期限を調べる。更新候補は正確なバージョンと公開日で示す。
4. 経歴・実績・サービス・掲載リポジトリ・説明文・リンクの更新候補を点検する。公開情報、このリポジトリ、利用者が指定した資料だけを根拠とし、別プロジェクトの非公開情報・推測の経歴・推薦文を追加しない。事実確認が必要なら変更案と質問を提示する。
5. 毎日は新規差分・障害を優先する。週1回（日曜日）は全リンク、表示、アクセシビリティ、生成経路、依存のサポート状況まで広げる。UIの主張には実ブラウザの根拠を付ける。
6. 新規または重要な変化のある提案、失敗、利用者の判断が必要な事項のみ通知する。同じ承認待ち・保留・却下済み提案は根拠が変わるまで再通知しない。改善のためだけに毎日変更を作らない。

### 実行と引継ぎ

- 最初に標準の `$CODEX_HOME/automations/<id>/memory.md` を読む。実行終了時と利用者の判断・PR状態が変わった時に、提案ID、対象・バージョン、提案スレッドID、判断の原文と日時、PR URL、最終確認commit・run_id、残る未確認事項を短く更新する。承認の正本は利用者の発言であり、メモだけを根拠に実行権限を広げない。過去スレッドを参照できない場合は、既存提案のスレッドでの回答を案内し、重複提案を作らない。
- 提案IDは日付だけで採番せず、`YYYY-MM-DD/<thread-id先頭8桁>/<連番>` とする。同じ対象・同じ目標バージョンは既存IDを継続する。解決済みの履歴はPRへの参照に縮約し、全履歴を毎回読み込まない。
- `bash scripts/maintenance-check.sh` で公開状態と両言語の依存監査を実行する。各検査の終了結果と一時レポートを読む。`OK` はコマンド成功であり、main・run・公開JSONの一致は別途照合する。通信失敗時は権限・接続を一度確認し、同じ失敗を繰り返さない。未完了の必須検査があれば提案は準備中とし、承認を求めない。
- 日次は対象ファイルを直接読み、`node_modules`、生成物、全セッション、全バージョン履歴を列挙しない。依存更新は `pnpm outdated --format json` と候補バージョンの公式情報に絞り、公開日時は `npm view <package> time --json` の取得結果から対象キーだけ出力する。完全な出力は一時ファイルへ保存し、画面には要約・必要な根拠だけを出す。
- CIの監査結果を参照する場合は検証日時・対象SHAを添え、当日の監査を実施した扱いにしない。Node・pnpm・Python・Actionsのサポート状況も省略せず、前回から変更がなければ確認結果を短く記録する。

## 更新の選定

- 通常更新は安定版かつ公開から7日以上経過したものを候補とする。新しいだけの更新や、情報不足・監査不能は保留にする。
- 既知脆弱性の緊急修正で待機期間の例外が必要なら、対象バージョン、勧告、緊急性を示し明示承認を得る。既存の供給元検証・ハッシュ・インストール制約を黙って緩和しない。
- メジャー更新は別提案にする。通常更新は互換性が関係する依存だけをまとめ、更新前後の全依存ツリーを監査する。low/moderateも報告し、修正版が適合すれば解消する。
- 監査合格は既知の脆弱性が検出されない根拠であり、安全性全体の保証ではない。公式勧告、リリース差分、供給元の変化、lockfile、実ビルドも確認する。
- 互換層、旧コードの分岐、二重書込み、旧ワークフローを恒久化しない。移行が必要なら切替・検証・旧処理撤去までを同じ変更で完了する。恒久overrideを安易に追加せず、既存overrideも必要性を確認する。

## 提案と承認

提案IDごとに、目的、根拠URL・確認日時、対象ファイル、変更前後の内容・バージョン、分離したcheckoutで準備した差分、検証結果、リスク、未確認事項、公開への影響を示す。内容の意味・必要情報が未確定なら、実装可能と装わず確認待ちにする。

更新候補の列挙は承認用の提案ではない。固定バージョンは `package.json` とlockfileを一緒に変更し、互換性上の関係がない更新を一括承認にまとめない。通常更新でも公式リリース差分・勧告と更新後の監査・ビルドを確認してから承認を求める。

承認前は調査とローカルの差分準備まで。元checkoutのindex操作、commit、push、PR作成、merge、公開、GitHub設定変更は行わない。日次提案への沈黙や経過時間を承認にしない。

利用者が対象提案を「PR作成からマージまで承認」と指示したターンで、最新mainとの整合を確認し、`codex/`ブランチで実装・検証・commit・push・PR作成を行う。既存の無関係な差分を混ぜない。承認範囲内の修正・検証は繰り返し許可を求めず進める。新しいGit index操作・commitはそのターンの明示権限に従う。

独立レビュー、必要な実ブラウザ確認、PRの最新headに対する必須CI、未解決レビューがないことを確認してマージする。headが変わった場合は差分と検証の有効性を再確認する。管理者バイパス、force push、検証省略は使わない。承認を超えるメジャー変更、内容の意味変更、別目的の変更は再提案する。

マージ後は対応するActionsの公開成功と公開先 `build.json` を照合し、ページ・データ・規約の到達を確認して完了報告する。公開失敗はマージ済みと分けて報告し、未承認の追加変更を自動マージしない。後続のスケジュールは既存承認の範囲でPR・公開を追跡できるが、将来の別提案を承認済みと扱わない。

## 実行環境

ローカルファイルを扱うCodex実行時は、PCとアプリが起動し、このリポジトリとGitHub認証が利用可能であることが必要。環境不備は点検未実施として報告する。
ローカルのPython監査は既存の `requirements.txt` から `.venv/` に準備する。uv管理のPython 3.11を使用し、CIと同じminor version・既存の依存定義を使う。Codexのネットワーク設定はプロジェクトの `.codex/config.toml` を参照する。設定変更後はCLI試行だけで完了とせず、アプリのスケジュール実行で通信・監査・引継ぎを確認する。
PR用データは `tests/fixtures/data/` の固定サンプルと現行YAMLから生成する。実公開ではこのサンプルを利用せず、必要なAPI取得に失敗したら公開を止める。
