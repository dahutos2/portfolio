# 更新提案

会話由来の掲載内容を主対象とし、掲載候補または掲載不足に関する確認事項が見つかった時だけ読む。日次の確認を一括で再実行しない。

- 通常更新は公開7日以上の安定版。新しいだけの更新、必要性・互換性・根拠が不明なものは保留する。緊急脆弱性修正の待機例外は、勧告・対象版・緊急性を示し明示承認を得る。
- メジャー更新は別提案。通常更新も互換性が関係する依存だけまとめる。既存overrideの必要性を確認し、供給元検証・ハッシュ・インストール制約を緩めない。監査は安全性全体の保証ではないため、公式リリース差分・勧告・供給元・lockfileも確認する。
- `pnpm outdated --format json` と候補の公式情報に絞る。`npm view <package> time --json` の完全出力は一時ファイルへ置き、対象版の日時だけ読む。
- 分離したcheckoutで実差分を準備し、固定版はpackage.jsonとlockfileを一緒に変更する。更新後の依存ツリー監査（low/moderateも報告）、型検査・ビルド・必要なブラウザ検証を行う。PR用データは `tests/fixtures/data/` と現行YAMLを使う。理由を問わず必須検査が未完了なら準備中とし、承認を求めない。追加接続・インストールも既存の許可範囲に従う。
- 掲載内容は公開情報・当該リポジトリ・利用者の指定資料とローカルCodex履歴で裏付ける。中央のportfolio専用手順で抽出した候補を現行 `portfolio.config.yml` と比較し、公開可能な表現を利用者に確認する。会話の読取り許可を公開許可にせず、計画やassistantの報告だけで完了実績としない。根拠発言・非公開メモはブランチ、PR本文、commitメッセージへ転記しない。意味や事実が未確定でも、根拠の範囲で推定した掲載案と確認箇所を先に示し、公開可能と確定しない。
- 不要な互換層・旧分岐・二重書込み・旧ワークフローを残さない。移行するなら切替・検証・旧処理撤去を同じ変更で終える。

提案IDは `YYYY-MM-DD/<thread-id先頭8桁>/<連番>`。同じ対象・目標版は既存IDを使う。提案ごとに目的、公式根拠URLと確認日、正確な版・公開日、対象ファイルと実差分、検証、リスク・未確認事項・公開への影響を示す。候補の羅列だけで承認を求めない。

難しいセキュリティ判断、認証・秘密情報・移行、複雑な設計はAstraへの手動切替が必要と明記し、根拠・範囲・不明点を引き継ぐ。承認とモデル切替を確認して着手する。通常の日次・小修正のモデルはスケジュールを正本とする。

承認を受けた場合だけ[承認後の作業](delivery.md)を読む。

## 掲載改善の到達条件

経歴の期間・本人の役割・成果、提供サービスを裏付ける経験、掲載実績との対応を現行YAMLから点検する。日付の空白やリンク不足は確認のきっかけであり、欠落した実績がある証明ではない。履歴の日時を活動日へ流用しない。項目を埋めるために推薦文や経歴を作らない。

優先する不足1〜3件について「対象YAML項目／現在の記載／根拠から示せる公開用変更案／未確定事項」をこの提案スレッドで示す。会話の明記事実・推定・根拠なしを区別し、未確定でも根拠のある範囲で控えめな掲載文を先に作る。利用者に経歴を一から列挙させず、その文面の採否・修正箇所を確認する。期間を裏付けられなければ日付を作らず、日付未確定の経歴案または既存サービス文の案として示す。uncertainの保存だけで終えない。既存候補と過去の判断を先に確認し、同じ質問は根拠変化なしに繰り返さない。非公開名・引用は質問や変更案にも出さず一般化する。

公開表現と事実が確認できたらYAMLの実差分を準備し、既存の生成・検証・PR手順へ進む。未確認の推定案はこのスレッド内に提示し、公開用YAMLやGitへ書かない。計画を完成実績に変えず、AIへの実装依頼だけから本人が全コードを実装したと推定しない。根拠が本当にない場合だけ調査範囲と限界を示し、架空の案を作らない。「候補なし」と「調査不足」「本人回答待ち」「現行記載で充足」を区別して報告する。CI成功を掲載充足の証拠にしない。profile等の既存YAMLにない項目を追加する場合は、消費側の仕様確認と別の変更判断が必要。
