# 承認後の作業

対象提案の実装・commit・push・PR作成を利用者が明示承認した時、既存PRの状態変化を追跡する時、または利用者によるマージ後の公開確認時だけ読む。追跡は読み取りだけで行い、新しい変更・Git操作の権限としない。

1. 提案スレッドの承認原文と範囲を確認する。沈黙、メモ、過去の包括承認や別提案の承認から権限を広げない。最新main・作業ツリーと準備済み差分を照合し、`codex/`ブランチで承認範囲を実装する。変更された根拠は再検証する。範囲内の修正・検証は許可を反復して求めない。
2. 共通Skillに従う独立レビュー、必要な実ブラウザ検証、最新headの必須CI、未解決レビューなしを確認する。管理者バイパス・force push・検証省略を使わない。別目的・承認外のメジャー変更や意味変更は再提案する。
3. PR URL・最終head・差分・検証結果・制約を渡し、利用者のマージを待つ。[入口](../maintenance.md)の最終マージ境界を守る。
4. 利用者がマージしたら、対応するActionsの公開成功と `build.json` を照合し、ページ・データ・規約HTML/PDFの到達を確認する。収集・CI・公開・実画面の成功を区別する。失敗はマージ済みと分けて報告し、追加修正は別PRで利用者のマージを待つ。
5. 掲載候補に対応するPR・公開を確認したら、中央のportfolio専用手順で候補の判断状況と参照先を記録する。通知した変化も同手順で記録する。完了詳細はPRに残し、公開状態の正本を複製しない。

本番公開は既存Actionsが担い、固定サンプルを使わず必要なAPI取得失敗で止める。同じGitHub認証を使うCodexと人間をGitHub側で区別できないため、この運用を技術的な権限分離とは扱わない。
